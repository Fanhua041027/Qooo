# 农间诊 MVP 产品需求文档

## 1. 产品定义

### 核心问题

农户发现叶片、果实或植株异常时，通常不知道问题是什么，也不知道下一步该做什么，容易错过处理窗口或错误用药。

### MVP 唯一目标

用户可以在微信小程序中上传一张作物照片，得到清晰的初步判断、风险等级和下一步行动，并把行动加入农事任务，之后可以回看诊断记录。

### 成功指标

首版发布后，用以下指标判断核心价值是否成立：

- 从首页进入上传页的用户中，至少 70% 成功提交一张合格图片。
- 成功提交图片的用户中，至少 90% 在 30 秒内看到诊断结果状态（真实结果或明确处理中状态）。
- 至少 60% 的诊断结果包含一条用户可执行的农事行动。
- 诊断结果页“创建农事任务”的点击率达到 20%。
- 图片质量失败后，至少 50% 的用户能根据提示重新提交成功。

### 不在 MVP 解决的问题

- 视频问诊和实时通话
- 农资商城、复杂支付和分佣
- 农产品交易
- 社区内容生态
- 物联网设备接入
- 多专家会诊
- 产量预测

## 2. 版本范围

### P0：必须完成

| 编号 | 功能 | 用户价值 | 实现决策 |
| --- | --- | --- | --- |
| P0-01 | 微信登录或模拟登录 | 识别用户并保存记录 | 开发环境可模拟；接口和用户态必须真实存在 |
| P0-02 | 首页 | 让用户立即开始诊断 | 必须真实实现页面和导航 |
| P0-03 | 农场/地块基础信息 | 让诊断结果带上作物和地块上下文 | 数据可先用本地/Mock，数据结构必须可持久化 |
| P0-04 | 拍照上传 | 提交异常图片 | 相机/相册选择必须真实实现 |
| P0-05 | 图片质量提示 | 降低模糊、过暗、主体不全导致的误判 | 客户端提示必须真实；服务端复核可 Mock |
| P0-06 | AI 诊断结果 | 告诉用户可能发生了什么 | 通过真实 API 契约；模型可先 Mock |
| P0-07 | 风险等级与处理建议 | 告诉用户下一步怎么做 | 规则和展示必须真实，不能仅靠前端写死 |
| P0-08 | 诊断历史 | 支持回看和复查 | 必须有持久化接口；开发阶段可用 Mock 数据源 |
| P0-09 | 创建农事任务 | 把建议转成行动 | 创建、完成、逾期状态必须真实可操作 |
| P0-10 | 消息提醒 | 不让用户错过结果和任务 | 站内消息必须真实；微信订阅消息可延后 |
| P0-11 | 简单管理后台/运营配置 | 调整诊断文案、风险和推荐动作 | 页面和配置结构必须真实；首版可用本地 Mock 数据 |
| P0-12 | JEV 诊断行动闭环 | 让判断、执行和复查形成可追踪循环 | 诊断结果、农事任务和复查接口必须共享 `loop` 状态；模型仍可 Mock |

### P1：P0 稳定后再做

- 视频问诊
- 语音输入和语音播报
- 专家图文复核
- 更完整的知识库与相似案例
- 天气预警和按地块天气
- 组织/合作社协作
- 农资推荐，但不做完整商城
- 诊断报告导出

### P2：验证核心价值后再做

- 农资商城
- 农产品交易
- 社区
- 物联网设备
- 多专家会诊
- 复杂支付和分佣
- 产量预测
- 设备自动控制

## 3. 核心用户流程

```text
登录/模拟登录
  → 首页
  → 选择农场/地块和作物
  → 拍照或从相册选择
  → 图片质量检查
  → 提交诊断
  → 查看可能问题、风险等级、处理建议
  → 创建农事任务
  → 任务提醒
  → 在诊断历史中复查
```

## 4. 用户故事与验收标准

### P0-01 微信登录或模拟登录

**用户故事**：作为农户，我希望快速进入小程序并保留自己的诊断记录，这样我下次可以继续查看。

**验收标准**：

1. 首次进入时显示登录/模拟登录入口，点击后进入首页。
2. 开发环境点击“模拟登录”后生成稳定的测试用户 ID；刷新页面不会丢失登录态。
3. 未登录访问诊断历史、农场和我的页面时，系统引导登录，不出现空白页。
4. 退出登录后，个人数据不会被展示给下一个用户。
5. 生产环境保留替换为微信 `code` 登录的接口位置，不允许把用户 ID 永久写死在页面代码中。

### P0-02 首页

**用户故事**：作为农户，我希望打开小程序就能看到“拍照诊断”入口，不需要学习复杂菜单。

**验收标准**：

1. 首页首屏存在唯一主操作“拍照诊断”。
2. 从首页到上传页最多点击 1 次。
3. 首页能看到当前农场/地块摘要、最近一次诊断和待处理任务。
4. 没有数据时显示可执行的空状态，例如“先添加一块地”或“拍一张开始诊断”。
5. 断网时显示明确的离线提示，不显示伪造的成功状态。

### P0-03 农场和地块基础信息

**用户故事**：作为农户，我希望保存农场、地块和作物信息，这样诊断时可以提供更准确的上下文。

**验收标准**：

1. 用户可以创建农场，至少填写名称和所在地区。
2. 用户可以在农场下创建地块，至少填写地块名称、作物和种植日期。
3. 诊断提交前可以选择已有地块，也可以跳过并在之后补充。
4. 刷新或重新进入小程序后，已保存的农场和地块仍可查看。
5. 删除地块前必须二次确认；已有诊断记录不会被静默删除。

### P0-04 拍照上传

**用户故事**：作为农户，我希望直接拍摄异常部位或从相册选择照片，以便提交诊断。

**验收标准**：

1. 用户可以调用相机，也可以从相册选择图片。
2. 上传页展示拍摄示例：主体完整、靠近病斑、避免逆光和反光。
3. 支持重新选择、删除和预览图片。
4. 提交按钮在没有图片时不可用，并给出原因。
5. 图片提交后显示上传进度或处理中状态，重复点击不会创建重复诊断。
6. 上传失败时可以重试，已选图片不会无故丢失。

### P0-05 图片质量提示

**用户故事**：作为农户，我希望在提交前知道照片是否太模糊、太暗或看不清主体，避免得到不可靠的诊断。

**验收标准**：

1. 系统至少检查图片尺寸、清晰度、亮度和是否存在可识别主体。
2. 不合格图片必须显示具体原因，例如“画面偏暗，请移到自然光下重新拍摄”。
3. 质量提示必须提供下一步动作：重新拍摄、继续提交或查看拍摄示例。
4. 对轻微问题允许用户明确确认后继续提交，并在诊断结果中标注“图片质量有限”。
5. 检查失败不能阻塞整个页面；无法检测时允许进入服务端检查。

### P0-06 AI 诊断结果

**用户故事**：作为农户，我希望看到系统对作物异常的初步判断，并知道判断依据和不确定性。

**验收标准**：

1. 提交后显示处理中状态，包含预计等待提示或进度阶段。
2. 结果至少包含作物、可能问题、置信度/可信程度和判断依据。
3. 结果明确标识“辅助判断”，不能用绝对语气替代专家诊断。
4. 低置信度时显示“建议补拍”或“建议人工复核”，不能伪装成确定结论。
5. 诊断失败时提供重试和人工求助入口，不能停在无限加载。
6. 每条结果记录诊断时间、图片、地块、模型版本和请求 ID，便于追踪。

### P0-07 风险等级与处理建议

**用户故事**：作为农户，我希望知道问题有多紧急，以及现在可以采取什么安全动作。

**验收标准**：

1. 结果页显示低、中、高三级风险，并说明等级含义。
2. 每个结果至少给出一条具体、可执行的下一步行动，包含时间或条件。
3. 建议区分“现在做”“观察什么”“暂时不要做”。
4. 涉及药剂时必须显示适用作物、安全间隔期和风险提示；没有可靠数据时不得编造剂量。
5. 高风险或低置信度结果必须提供“请专家复核”或“补充图片”入口。
6. 处理建议由配置/规则返回，不能只在前端硬编码一段固定文案。

### P0-08 诊断历史

**用户故事**：作为农户，我希望回看过去的诊断和处理结果，以便比较问题是否改善。

**验收标准**：

1. 历史列表按时间倒序展示，至少显示缩略图、作物、问题、风险和状态。
2. 点击记录可以进入与当时一致的结果详情。
3. 支持按农场/地块和状态筛选。
4. 空历史时给出“开始第一次诊断”的入口。
5. 删除记录需要二次确认，并保留服务端审计记录。

### P0-09 创建农事任务

**用户故事**：作为农户，我希望把处理建议变成任务并收到提醒，避免看完建议后忘记执行。

**验收标准**：

1. 结果页可以一键创建任务，默认带入建议标题、地块和建议时间。
2. 用户可以修改任务名称、执行时间、负责人和备注。
3. 任务至少支持待处理、已完成、已逾期三种状态。
4. 任务完成后可以添加备注或照片。
5. 创建成功后返回任务详情或任务列表，并且刷新后仍存在。

### P0-10 消息提醒

**用户故事**：作为农户，我希望知道诊断完成和任务到期，不必一直停留在页面等待。

**验收标准**：

1. 诊断完成、诊断失败、任务临近到期和任务逾期至少产生站内消息。
2. 消息列表展示未读数量、时间、类型和跳转目标。
3. 点击消息后能进入对应诊断或任务详情，并更新已读状态。
4. 用户可以关闭非必要提醒；高风险提醒不能被静默丢弃。
5. 微信订阅消息未接入时，必须在产品内明确显示“站内提醒”，不能假装已发送微信通知。

### P0-11 简单管理后台/运营配置页

**用户故事**：作为运营人员，我希望调整风险等级文案、建议动作和首页推荐，而不必每次发版。

**验收标准**：

1. 管理页至少可以查看和编辑风险等级说明、处理建议模板和首页提示。
2. 保存前显示变更预览，保存后记录修改人、时间和版本。
3. 配置错误时保留上一版可用配置，不能让小程序显示空白。
4. 未授权用户不能访问配置页或保存配置。
5. 首版可以用本地 Mock 数据，但必须保持与未来服务端配置相同的字段结构和校验规则。

## 5. 质量底线

- 所有关键页面覆盖加载中、空数据、失败、无网络和重试状态。
- 诊断相关页面不使用绝对诊断语气。
- 任何药剂建议没有可靠来源时只给出“咨询当地农技员”的行动，不生成具体用量。
- 诊断请求必须幂等，避免重复点击造成多条记录。
- 重要操作给出明确反馈，不能只依赖颜色表达状态。
- 设计与交互遵循 `QdUI` 组件规范，组件状态完整，移动端拇指操作区域足够大。
