# 农间诊 AI 诊断 MVP 规格

## 目标

首版只提供农业辅助判断。系统必须稳定回答四个问题：图片能不能用、可能是什么、现在该做什么、是否需要补拍或转专家。模型可以替换，接口字段、规则和审计记录不能随供应商变化。

## 处理链路

```text
图片上传
  → 图片质量门禁
  → 作物与部位确认
  → 多模态模型生成候选和可见证据
  → 规则引擎校准分数并决定 RESULT / ASK_MORE / EXPERT_REVIEW
  → 安全过滤
  → 生成 DiagnosisRecord
  → 保存模型、提示词、规则、知识库版本和 requestId
```

## 图片质量门禁

| 检查项 | 拦截阈值 | 警告阈值 | 用户动作 |
| --- | ---: | ---: | --- |
| 短边尺寸 | `< 640px` | 无 | 使用原相机重新拍摄 |
| 清晰度 | `< 0.35` | `< 0.55` | 对焦异常部位并保持稳定 |
| 亮度 | `< 0.12` 或 `> 0.93` | `< 0.22` 或 `> 0.85` | 改善光线或避开反光 |
| 主体占比 | `< 0.08` | `< 0.20` | 让异常部位占画面三分之一以上 |
| 遮挡比例 | `> 0.70` | `> 0.45` | 移开遮挡物后补拍 |

阈值是 MVP 初值，不能宣传为通用农业标准。上线后根据“重拍后诊断成功率”和专家复核结果调整。客户端可做尺寸检查，其余指标应由服务端图片质量模型或图像算法生成。

## 分数和决策规则

## JEV 决策闭环

诊断结果采用 JEV（Judgment、Execution、Verification）模型管理后续行动：

- `JUDGMENT`：完成图片判断，展示风险、依据和第一步行动。
- `EXECUTION`：用户把建议创建为农事任务，任务记录 `diagnosisId`，形成可追踪执行项。
- `VERIFICATION`：任务完成后，用户回到诊断结果提交“有改善、没变化、更严重、暂时看不出来”。
- `CLOSED`：复查显示有改善，本轮闭环完成。
- `REASSESSMENT`：没有改善或变严重，提示重新拍摄并进入下一轮判断；不会把原结果改写成新的确诊结论。

JEV 的 Loop 状态存放在诊断结果的 `loop` 字段，真实接口使用 `POST /api/v1/diagnoses/{id}/verify` 更新，Mock 与真实 API 共用同一份枚举。模型仍只负责辅助判断，Loop 负责把判断变成可验证行动。

- 模型分数只用于候选排序，不称为“正确概率”。
- 少于两条可见证据时，分数上限为 `0.64`，不能直接显示命名结果。
- 没有易混淆问题时，分数上限为 `0.84`。
- 图片只有警告时，分数上限为 `0.75`。
- 第一候选低于 `0.65`：转专家复核。
- 第一、第二候选都不低于 `0.55` 且差值小于 `0.12`：转专家复核。
- `HIGH`、`CRITICAL`、大面积暴发、连续处理无效或命中强制升级清单：转专家复核。
- 图片不合格、作物无法确认或没有候选：要求补拍，不展示病名。

风险等级和置信度必须分开：风险表示若判断成立可能造成的影响，置信度表示当前证据是否足以区分候选。

## 模型输出约束

模型最多返回三个候选。每个候选必须包含病害名称、排序分数、风险等级、至少两个可见证据和至少一个易混淆问题。建议只允许观察、隔离、清洁、通风、灌排和复查等非化学措施。

禁止输出：

- “百分之百确诊”“肯定是”等绝对诊断语言；
- 未经实时登记核验的具体农药商品、有效成分、固定剂量和混配方法；
- 固定安全间隔期；
- 禁限用农药替代或规避监管方法。

安全过滤失败时不向用户展示原文，统一显示农业专家提供的安全提示，并记录违规代码供运营复盘。

## 专家复核触发条件

- 高风险或毁灭性问题；
- 第一、第二候选难以区分；
- 模型分数低于命名阈值；
- 用户描述大面积暴发；
- 用户连续处理但没有改善；
- 命中 `data/agriculture/ai-review-policy.json` 的强制升级清单；
- 涉及人员或牲畜接触农药后不适。

最后一种情况应提示立即联系当地医疗或应急渠道，农业诊断流程不得继续给出用药建议。

## 版本和审计

每条诊断必须记录：

```json
{
  "model": {
    "provider": "provider-name",
    "name": "vision-model-name",
    "version": "provider-model-version",
    "promptVersion": "diagnosis-prompt-1.0.0",
    "policyVersion": "1.0.0-mvp",
    "knowledgeVersion": "1.0.0-mvp"
  },
  "requestId": "req_..."
}
```

服务端审计日志还要保存输入图片的对象存储 ID 和哈希、脱敏后的用户描述、模型原始响应、规则引擎结果、最终展示结果、耗时和错误码。日志不得保存临时签名 URL，避免过期和泄露。

## 固定评测集

`data/diagnosis-evaluation/manifest.json` 提供四张合成图片，用于验证过暗、主体过小、遮挡和正常图片的 UI/质量门禁。它们不代表真实病害，不能用于准确率结论。

真实模型上线前，农业专家与 AI 工程师共同建立至少 50 张独立田间评测图。每张必须记录来源许可、专家标签、作物、生长部位、风险和易混淆问题。发布门槛建议为：

- 图片质量错误拦截召回率不低于 90%；
- 强制转专家案例召回率为 100%；
- 禁止文案和固定用药剂量拦截率为 100%；
- Top-1、Top-3 只作为内部指标，并按作物分别统计；
- 同时统计误诊率、漏诊率、补拍率和专家推翻率。

## 对接方式

`@nongjianzhen/diagnosis-engine` 是后端唯一规则入口：

- `evaluateImageQuality()`：质量门禁；
- `buildDiagnosisPrompt()`：构造供应商无关提示词；
- `assessDiagnosis()`：校准候选并决定是否追问或转专家；
- `checkDiagnosisSafety()`：拦截绝对诊断和未经核验的用药内容。

第三方模型适配器只负责把图片和上下文发送给供应商，再把响应映射成 `DiagnosisCandidateInput`。适配器不能自行绕过规则引擎直接生成前端响应。

模型原始输出需先通过 `validateModelOutput()`；对应的供应商结构化输出 Schema 位于 `packages/diagnosis-engine/schema/model-output.schema.json`。校验失败统一返回模型输出错误并进入重试或人工复核，不能猜测或静默补齐关键字段。
